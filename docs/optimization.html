Speed and memory optimization

Large linkage disequilibrium (LD) matrices increase both the computational work and memory needed for fine-mapping. prusie reduces repeated work and storage by reusing component products, limiting passes over the input and avoiding extra matrix allocations where possible.

These optimizations preserve the chosen statistical model, priors, stopping rules and variant order. Some regroup floating-point operations, so agreement with susieR is assessed numerically; see computational compatibility. Implementation describes the fitting routes, and Performance reports runtimes and memory for the inputs, settings and hardware measured there.

The current benchmark measurements compare prusie and susieR 0.16.6 on 200 FinnGen T2D GWAS loci and 14,157 GTEx Whole_Blood eQTL genes, with three retained complete calls per case on exclusive EPYC 7742 nodes. Across-case within-case R/prusie median-time ratios are 49.2× complete-call and 55.4× fitting-stage on GWAS, and 26.6× and 29.8× on eQTL; prusie was faster than susieR in every case on both panels. These are paired runtime results; the per-panel memory and thread-scaling comparisons on the performance page record their own gains and limitations.

Principles

The optimizations reduce the work needed to evaluate the SuSiE updates while retaining float64 arithmetic. They introduce no LD thresholding, variant pruning or low-rank approximation. Grouping exactly equal or opposite matrix columns changes only the matrix calculation: posterior probabilities remain separate for every variant. Single-effect components are still updated in sequence, using the latest residual.

Specialized calculations check input layout, dimensions, numerical bounds and exact equality where required; vector instructions also require CPU support. Implicit scaling and grouped matrix products fall back to the general calculation when numerical checks fail. The decision to discover exact-column classes uses deterministic work counts rather than timings collected during the fit.

Equivalent formulas can have different floating-point results when they regroup products or sums. Numerical validation compares the complete final alpha matrix with pinned susieR under matched inputs and fitting settings, in the original component and variant order. The computational compatibility criterion defines the tolerance; numerical accuracy reports the tested configurations and results.

Fewer passes over the input matrix

Reusing the input array

With the default overwrite_ld=False, preparation preserves the caller's LD array. An aligned, native float64 C-contiguous R or XtX can be reused by the dense solver: its transpose is a column-major view of the same storage. Dtype conversion, alignment repair and conversion to C order can require copies. Further arrays may be needed for symmetry repair, scaling or retained analysis; see Memory.

Combined validation

The validation-only traversal checks finiteness, nonnegative diagonal entries and exact symmetry together, visiting transposed pairs in tiles without a p×pp\times pp×p temporary. For ordinary RSS with LD matrix R\mathbf RR and known sample size nnn, including bhat/shat without var_y, the symmetry comparison uses (n−1)Rij(n-1)R_{ij}(n−1)Rij​ and (n−1)Rji(n-1)R_{ji}(n−1)Rji​. Without nnn, it compares the raw LD entries. Inputs describes the required checks and the additional diagnostics enabled by check_input=True.

On x86-64, a vectorized proof can accept contiguous LD whose diagonal is within 10−810^{-8}10−8 of one, whose entries have magnitude at most 1+10−81+10^{-8}1+10−8 and which is exactly symmetric. A guard on the RSS multiplier protects off-diagonal scaling from overflow, and the scaled diagonal is checked explicitly. A successful proof establishes the validation result without a further general traversal. If it fails, the general checks decide whether the matrix is valid.

Fused validation and repair

If the pair comparisons detect asymmetry, prusie emits a RuntimeWarning and averages the checked matrix with its transpose. For known-nnn RSS, scaling by n−1n-1n−1 precedes averaging. Repair writes the same computed value to both triangles and checks the averaged entries for finiteness and a nonnegative diagonal during that traversal.

With overwrite_ld=False, susie_rss with known n, var_y=None and a plain, aligned, C-contiguous float64 NumPy R can combine validation and repair. Unless the symmetry proof accepts the input, this route allocates a private repair buffer and fills it while checking the raw and scaled inputs. The buffer is retained for asymmetric input and discarded for symmetric input. When fusion is unavailable, validation and required repair use separate traversals. The asymmetry warning precedes any error found in the repaired values.

n_threads defaults to 1. For eligible RSS inputs with p≥1024p\ge1024p≥1024, a larger value can parallelize the proof and owned repair. Preparation workers join before subsequent Python transformations or warnings. Warning display, recording, logging capture and tracing do not determine eligibility. Unsupported parallel preparation uses the serial calculation. Caller callbacks must not modify input arrays during a fit; see Threads.

The opt-in overwrite_ld=True can instead use the caller's R for repair after finding a finite asymmetric pair in the scaled matrix. Once writes begin, later errors or warnings promoted to exceptions can leave R and its aliases changed. Reload the original LD before reuse, including after a failed call. Optional LD workspace describes the supported storage and options.

Implicit scaling

Let M\mathbf MM be the input matrix after any repair and D=diag⁡(d1,…,dp)\mathbf D=\operatorname{diag}(d_1,\ldots,d_p)D=diag(d1​,…,dp​) contain the predictor scale factors. The working matrix is Q=a D−1MD−1\mathbf Q=a\,\mathbf D^{-1}\mathbf M\mathbf D^{-1}Q=aD−1MD−1. For ordinary RSS with known nnn and unrepaired M=R\mathbf M=\mathbf RM=R, a=n−1a=n-1a=n−1; otherwise a=1a=1a=1, including when repair has already incorporated that factor. For a vector v\mathbf vv of length ppp, the solver can apply

Qv=a D−1{M(D−1v)} \mathbf Q\mathbf v =a\,\mathbf D^{-1}\{\mathbf M(\mathbf D^{-1}\mathbf v)\} Qv=aD−1{M(D−1v)}

without storing Q\mathbf QQ. This adds O(p)O(p)O(p) vector scaling per product. The native guard admits this calculation when 1≤a≤1091\le a\le10^91≤a≤109, every djd_jdj​ and stored reciprocal 1/dj1/d_j1/dj​ lies in [0.5,2][0.5,2][0.5,2], and every ∣Mij∣≤2×109\lvert M_{ij}\rvert\le2\times10^9∣Mij​∣≤2×109. The entry checks also establish finiteness. Outside these bounds, the solver materializes the scaled matrix once and checks that its entries remain finite.

The bounds protect prepared matrix entries, while individual products still need finiteness checks. A nonfinite intermediate or result in the factored calculation causes that product to be recomputed with a temporary materialized matrix. The formulas agree in exact arithmetic, but regrouping the operations can change floating-point results. When Python must prepare the full working matrix, its fallback uses one output array, with an AVX-512 helper where supported or NumPy operations writing into that array.

Matrix products in the sweep

Retained component products

Dense matrix–vector kernel

The ordinary column-major kernel adds matrix columns in ascending order, skipping column jjj when its coefficient vjv_jvj​ is zero. An all-zero vector therefore reads no matrix columns, although clearing the output and scanning the coefficients still take O(p)O(p)O(p) work. Groups of four nonzero columns update each output element together, reducing output-vector loads and stores. Each element receives the same sequence of separate float64 multiplications and additions as in a column-by-column product.

On x86-64 an AVX2 build of this kernel is selected at run time when supported; otherwise the portable build is used. n_threads defaults to 1. Eligible large products can partition the output rows among threads while preserving each row's column order. Component updates remain sequential; see Threads.

Exact signed-column classes

Exactly equal or opposite LD columns allow repeated contributions to be combined within a product. The grouping uses the matrix actually multiplied: M\mathbf MM under implicit scaling, otherwise the materialized Q\mathbf QQ. If its ppp columns fall into ggg signed classes, prusie adds each class's signed coefficients with compensated summation and multiplies only its representative column. This costs O(pg)O(pg)O(pg) work. When a separate check proves the corresponding row relations, a stored g×gg\times gg×g matrix reduces the work to O(g2+p)O(g^2+p)O(g2+p), including coefficient grouping and expansion to all ppp output entries.

Discovery hashes 16 sampled entries per column, then complete columns within crowded buckets, to propose comparisons. Every accepted column relation is verified over all entries with exact float64 equality. The compact form also requires exact row relations. If the proved class count exceeds 7p/87p/87p/8, no plan is retained. These checks preserve separate posterior coordinates for every variant; no LD threshold or rounding defines a class.

Full discovery is delayed by a deterministic work-count rule. A product is dense for this rule when its coefficient vector has at least ⌈p/8⌉\lceil p/8\rceil⌈p/8⌉ nonzero entries. At the first dense product, sampled hashes give a lower bound on the class count. If this already exceeds 7p/87p/87p/8, or the columns are not contiguous, the operator abandons discovery. Otherwise, each ordinary dense product adds any positive estimated saving over a compact product to a running total, using its actual nonzero count. Once that total covers the estimated setup cost, the next dense product attempts full discovery. The fixed operation-count weights are defined in activation.rs; the decision uses no timings collected during the fit. A fit that finishes before reaching this threshold avoids full discovery. Sparser products always use the ordinary kernel and contribute nothing to the total.

Full discovery is attempted at most once per native operator, including when it returns no plan. Refinement can run several native fits, each with its own operator and discovery decision. A nonfinite class sum, scaled intermediate or grouped result causes that product to use the ordinary calculation. Regrouping coefficients changes floating-point arithmetic, so exact column relations do not guarantee bitwise equality with an ordinary product.

The full matrix remains allocated. A retained plan adds O(p)O(p)O(p) storage, plus g2g^2g2 values when the compact form is available. Individual-level designs and RSS models fitted with the Python sweep loop do not use this plan.

Searching for a component's prior variance repeatedly evaluates the same per-variant evidence. For component ℓ\ellℓ, ordinary Gaussian single-effect regression (SER) uses marginal estimates b^ℓj=rℓj/Qjj\widehat b_{\ell j}=r_{\ell j}/Q_{jj}bℓj​=rℓj​/Qjj​ and sampling variances sj2=σ2/Qjjs_j^2=\sigma^2/Q_{jj}sj2​=σ2/Qjj​ when Qjj>0Q_{jj}>0Qjj​>0; see the SER equations. With estimate_prior_variance=True and estimate_prior_method="optim" (the defaults), a scalar search evaluates the SER log marginal likelihood at multiple candidate prior variances VℓV_\ellVℓ​. Each evaluation takes O(p)O(p)O(p) work. The calculations below reuse quantities that remain fixed during that search.

Grouped sampling variances

Within a native Gaussian fit, the sampling variances and their groups are reused until σ2\sigma^2σ2 changes. For Bayes factors, finite sampling variances are floored at float64 machine epsilon. Grouping compares these floored values by exact equality. With at most 16 distinct values, the log term −12log⁡(1+Vℓ/s2)-\tfrac12\log(1+V_\ell/s^2)−21​log(1+Vℓ​/s2) and factor Vℓ/{s2(Vℓ+s2)}V_\ell/\{s^2(V_\ell+s^2)\}Vℓ​/{s2(Vℓ​+s2)} are computed once per group for each tested VℓV_\ellVℓ​. Search invariants

With grouping available and finite marginal estimates, 12b^ℓj2\tfrac12\widehat b_{\ell j}^221​bℓj2​ is computed once per component update and reused during its search. With equal log prior weights and finite squared estimates, the nonnegative group factors let per-group maxima determine the largest log weight needed for log-sum-exp. This avoids a separate scan over variants for that maximum. In this guarded case, the null objective at Vℓ=0V_\ell=0Vℓ​=0 is the common log prior weight plus log⁡p\log plogp.

The buffers belong to the current fit, and the estimate-dependent quantities are refreshed before each component's search. Fixed prior variances and estimate_prior_method="EM" skip preparation of these search invariants.

Vector exponentials

The search objective and posterior construction evaluate shifted exponentials exp⁡(xj−max⁡kxk)\exp(x_j-\max_k x_k)exp(xj​−maxk​xk​), where xjx_jxj​ is a log Bayes factor plus its log prior weight. Native GNU/Linux x86-64 builds can use glibc libmvec: four float64 values per AVX2 library call or two per SSE2 call, subject to symbol availability and CPU support. Scalar evaluation handles unavailable vector functions, tail values, nondefault rounding or enabled flush-to-zero and denormals-are-zero modes. Backend selection is cached; the dispatch checks the caller's control modes without changing them.

With the AVX2 exponential available, compatible control modes, equal prior weights and at most four sampling-variance groups, the search also fills log weights four at a time using separate multiplications and additions. The compile-time portable-math feature excludes the vector-math shim; see numerical reproducibility.

Summation of likelihood weights

The search objective adds its nonnegative exponentiated weights with a balanced pairwise tree. Each term passes through at most ⌈log⁡2p⌉\lceil\log_2 p\rceil⌈log2​p⌉ additions, and the tree overwrites scratch storage that the next objective evaluation reuses. Posterior weight normalization and signed objective reductions, including the ER2 dot products, retain compensated float64 summation.

Individual-level designs

During IBSS, susie uses the working design matrix X\mathbf XX directly, avoiding storage of its p×pp\times pp×p crossproduct. For a coefficient vector v\mathbf vv, it applies

Qv=XT(Xv). \mathbf Q\mathbf v=\mathbf X^T(\mathbf X\mathbf v). Qv=XT(Xv).

Column means and scales implement centering (intercept=True) and standardization (standardize=True) within these products. Sparse predictors use compressed sparse column (CSC) storage, and a positive null_weight adds a virtual zero column. A dense product takes O(np)O(np)O(np) work; a sparse product takes O(nnz+n+p)O(\mathrm{nnz}+n+p)O(nnz+n+p), including the vector operations, where nnz\mathrm{nnz}nnz counts stored design entries. Both use O(n+p)O(n+p)O(n+p) product workspace in addition to the design and the O(Lp)O(Lp)O(Lp) posterior arrays and retained component products.

Preparation can allocate dtype or layout copies and temporary arrays for column statistics. Credible-set construction separately forms requested correlation blocks, which can be dense even for sparse predictors.

For susie_trendfilter, the uncentered design is (−U)k+1(-\mathbf U)^{k+1}(−U)k+1, where Uij=1U_{ij}=1Uij​=1 for i≤ji\le ji≤j and zero otherwise, and kkk is order. Repeated cumulative sums apply the n×nn\times nn×n design and its transpose in O((k+1)n)O((k+1)n)O((k+1)n) work per product with O(n)O(n)O(n) product workspace.

susie_rss also uses a design operator for a single reference genotype matrix X, except with dynamic RSS models or reconstruction from bhat, shat and var_y, which form dense matrices. Product work depends on the reference row count; see supported input routes.

Memory

A dense p×pp\times pp×p float64 matrix uses 8p28p^28p2 bytes for its values. Memory planning also needs to account for copies, temporary workspaces, posterior arrays and optional diagnostics.

At p=5000p=5000p=5000, 8p2=200,000,0008p^2=200,000,0008p2=200,000,000 bytes, or approximately 190.7 MiB.

Input reuse and implicit scaling avoid extra full-matrix allocations when their conditions hold. Common sources of additional matrix storage are:

  • dtype, alignment or C-order conversion of the input;
  • owned validation and repair, including a temporary buffer that can be discarded after proving the input symmetric;
  • materialized scaling when the implicit-scaling guard fails, or a temporary scaled matrix when a factored product has a nonfinite intermediate or result;
  • maf filtering or a positive null_weight on a materialized-matrix route; design operators use a virtual null column;
  • reconstructed or updated RSS matrices, including the bhat/shat/var_y route, finite-reference and mismatch models, multiple reference panels and susie_rss_lambda; check_input=True also allocates eigenvectors on matrix-based routes;
  • read-only input snapshots for supported retained analyses. Within that scope, retain_data=True, tracking, refinement and model_init/s_init can retain matrix copies.

The core alpha, mu, mu2, lbf_variable and retained component-product arrays use O(Lp)O(Lp)O(Lp) storage, with O(p)O(p)O(p) vector workspace. An exact-column plan adds O(p)O(p)O(p) storage plus g2g^2g2 values for its compact form, where ggg is the number of signed classes; the full matrix remains allocated. In native IBSS fits, track_fit="dense" stores alpha, mu and mu2 for each recorded sweep, adding O(TLp)O(TLp)O(TLp) storage over TTT sweeps. Other trace contents are described under convergence diagnostics.

For a candidate credible set of mmm members, purity from a supplied matrix reads pair entries directly. With a min_abs_corr threshold and median_abs_corr=None, the first failing pair rejects the set before the pair-value vector is allocated. Sets that pass collect all m(m−1)/2m(m-1)/2m(m−1)/2 absolute correlations to report the minimum, mean and median, using O(m2)O(m^2)O(m2) storage. The optional cs_extension_corr step also forms candidate-by-all-variant correlation blocks. Purity from a design matrix forms the requested blocks as described under Individual-level designs.

In the real-data overwrite series, enabling overwrite_ld on 200 GWAS cases produced a material fresh-process peak-RSS reduction in 173 cases and no material saving in 27. The median within-case False/True peak ratio was 1.72. This is a measured process peak, including inputs and interpreter, rather than the matrix-size arithmetic above. The LD workspace contract describes ownership requirements and when the caller must reload its array.

Threads

IBSS components remain sequential: each update uses the latest residual from earlier updates in the sweep. Parallelism within a dense matrix product instead assigns disjoint output rows to workers. Each row retains its source-column accumulation order.

n_threads defaults to 1 and accepts integers from 1 to 32. With a larger value, eligible dense products use a private native pool. Dispatch requires at least 1024 output rows and 102421024^210242 matrix entries; compact products from exact signed-column classes use their reduced dimensions for this check. Smaller products, design operators and the Python dynamic RSS sweep are not parallelized by this option.

Eligible susie_rss calls can also parallelize the symmetry proof and owned repair. Preparation workers join before later Python transformations or warnings; overwrite_ld=True preparation is serial. The native threading contract describes the storage, build and floating-point requirements. Caller code, including callbacks and other threads, must not modify input arrays or their aliases during a fit.

PRUSIE_NUM_THREADS does not override the public n_threads option. The option leaves process-wide Rayon and BLAS settings unchanged. NumPy matrix operations, including those in dynamic RSS, follow their own BLAS threading settings, so n_threads=1 does not limit every operation in the Python process to one thread.

For an eligible dense fit, 2–4 threads are useful starting points; measure on the intended workload and keep BLAS at one thread when assessing this option. In the controlled thread scaling experiment on 87 fixed cases, median paired across-thread/one-thread complete-call ratios were 0.799 at two threads, 0.735 at four threads and 0.783 at eight threads. Four threads had the lowest ratio and improved every case; eight threads were slower than one in 8 cases and slower than four in 52. When running several fits concurrently, account for each fit's worker threads.

What prusie does not do

The optimizations described here retain float64 arithmetic. They do not threshold LD, prune variants or substitute a low-rank approximation. Variant filtering through maf and model options are explicit analysis choices. IBSS components retain their sequential update order.

prusie does not guarantee R's accumulation order or bitwise equality with susieR or across platforms. Regrouped operations and math-library implementations can change results. Numerical agreement is assessed on the complete final alpha matrix under matched inputs and fitting settings. The computational compatibility criterion defines the comparison, and numerical accuracy reports the tested configurations.
